# L2 simplified pipeline, version 2: group-batched execution

Version 2 keeps every rule of version 1 ([common.md](common.md), [plan.md](plan.md), [author.md](author.md),
[audit.md](audit.md), [repair.md](repair.md), [group-audit.md](group-audit.md)) and changes three things: the order in
which a group's steps run, how audits reach the run, and which records an audit compares against. Read the step's own
instructions first; this file says only what differs. A run started with `--pipeline simplified` uses version 2; a
version 1 run (`--pipeline simplified@1`, and every run started before version 2) keeps the version 1 order and
contract until it finishes.

## Order

After every plan of the slice is recorded, each group runs in turn:

1. **Draft every owned concept** of the group ([author.md](author.md)), each in its own fresh context, recorded with
   `l2 record author <id>` as before.
2. **First audits.** Only once every draft of the group is recorded, each concept gets its two independent first
   audits, A and B ([audit.md](audit.md)), with every sibling's record in place. The audits of the group's concepts
   may run concurrently.
3. **Repairs and re-audits**, as before: a blocking finding reopens the concept (`l2 reopen <id> --from-findings`), it
   is repaired ([repair.md](repair.md)), then re-audited by a fresh, independent auditor R.
4. **The group audit** (auditor G, [group-audit.md](group-audit.md)), then the next group.

The tooling refuses an audit of a group while any of its drafts is missing (`l2 submit-audit`, and the step order
of `l2 record audit`). Repair limits, the standing repair exception, signal coverage, record fingerprints, the
budget hook and every gate are unchanged.

## Independence

Each auditor works in its own fresh agent context. It is never shown another auditor's findings, note or artifact,
and never reads the run's findings directory or `l2 findings`; the orchestrator gives it only its task. Auditor B is
an independent first audit, not a review of A.

## Submitting findings

An auditor never writes the run state or a group file, and never runs `l2 record`. It writes its findings to a JSON
file in the work directory its task names, and submits it:

```bash
npm run map:author -- l2 submit-audit <concept> --role first-audit --auditor A --file <json>   # or --auditor B
npm run map:author -- l2 submit-audit <concept> --role re-audit --auditor R --file <json>
npm run map:author -- l2 submit-audit <group> --role group-audit --auditor G --file <json>
```

The file:

```json
{
  "verdict": "pass",
  "note": "What was checked (overlap per placement, territory and splits, representation, accuracy, depth). Advisory: ...",
  "findings": [
    {
      "severity": "blocking",
      "concept": "<id of the record the finding is in>",
      "criterion": "accuracy",
      "evidence": { "quote": "<the exact words from the record>", "location": "paragraph 2" },
      "action": "<what the repair must do, within the accepted territory>"
    }
  ],
  "resolutions": [{ "id": "<signal id exactly as `l2 signals` prints it>", "resolution": "<how it was judged>" }]
}
```

- `verdict` is `fail` exactly when at least one finding is `blocking` (severity as in l2-authoring.md, "Finding
  severity").
- Every finding names its concept (a group audit may name any owned member), gives evidence (a quote, which must
  appear verbatim in that record as it is now, a location, or both) and the action it requires.
- A passing first auditor resolves every signal of `l2 signals <concept>`; auditors A and B each resolve what they
  judged, and the recorded audit takes A's resolution where both resolved a signal. A re-auditor and a group
  auditor resolve the signals as in version 1.

`submit-audit` validates the file, binds it to the records it judged (the concept's record and its authored
neighbours', or every member's for a group audit) and publishes it as an immutable artifact under
`.map-authoring/l2/work/<run>/audits/`. A resubmission is a new artifact; nothing is overwritten, and an artifact for
records that have since changed is never used.

## Recording (the orchestrator only)

- `l2 findings <concept|group>` shows the artifacts submitted against the current records and what they support.
- `l2 record audit <concept>` records the concept audit from both first audits (or, after a repair, from the
  re-audit). It is refused while an auditor is missing, if A and B judged different versions of a neighbour, and on
  any blocking finding. `--audit-file` is refused in a version 2 run.
- `l2 reopen <id> --from-findings` opens the repair with the blocking findings as its reason (concept, auditor,
  criterion, action and evidence for each).
- `l2 record group-audit <group>` records the group audit from G's artifact the same way.

## Neighbours

A concept's overlap signals compare its record with its authored neighbours: in version 1, its group's members and
its hazard partners (and, since #243, owned members of other groups that list it). Version 2 adds every concept the
member excludes and the authored concepts its record names (at most 16, in id order, never its own ancestors, whose
texts are judged as parent overlap). Overlaps found there need a resolution like any other.

## Repair diff

When a concept is reopened, its record as the failing audit judged it is kept with the repair cycle.
`l2 repair-diff <concept>` prints, sentence by sentence and entry by entry, what the repair removed, added and kept,
and whether the record's form changed (`--json` for the full diff). The re-auditor reads it to scope the re-audit
([audit.md](audit.md), "Re-audit"): every changed statement, and anything it touches.

## Agent task descriptions

Name each agent task as the cost and budget tooling recognizes it: `Author <id>`, `First audit A <id>`,
`First audit B <id>`, `Repair <id>`, `Re-audit <id>`, `Group audit <group>`.
