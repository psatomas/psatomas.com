# L2 simplified pipeline, version 2: group-batched execution

Version 2 keeps every rule of version 1 ([common.md](common.md), [plan.md](plan.md), [author.md](author.md),
[audit.md](audit.md), [repair.md](repair.md), [group-audit.md](group-audit.md)) and changes three things: the order in
which a group's steps run, how audits reach the run, and which records an audit compares against. Read the step's own
instructions first; this file says only what differs. A run started with `--pipeline simplified` uses version 2; a
version 1 run (`--pipeline simplified@1`, and every run started before version 2) keeps the version 1 order and
contract until it finishes.

## Order

After every plan of the slice is recorded, each group runs in turn:

1. **Draft every owned concept** of the group ([author.md](author.md)), each in its own fresh context, recorded with
   `l2 record author <id>` as before.
2. **First audits.** Only once every draft of the group is recorded, each concept gets its two independent first
   audits, A and B ([audit.md](audit.md)), with every sibling's record in place. The audits of the group's concepts
   may run concurrently.
3. **Repairs and re-audits**, as before: a blocking finding reopens the concept (`l2 reopen <id> --from-findings`), it
   is repaired ([repair.md](repair.md)), then re-audited by a fresh, independent auditor R.
4. **The group audit** (auditor G, [group-audit.md](group-audit.md)), then the next group.

The tooling refuses an audit of a group while any of its drafts is missing (`l2 submit-audit`, and the step order
of `l2 record audit`). Repair limits, the standing repair exception, signal coverage, record fingerprints, the
budget hook and every gate are unchanged.

## Independence

Each auditor works in its own fresh agent context, started from its own prompt:

```bash
npm run map:author -- l2 audit-task <concept> --role first-audit --auditor A    # one prompt for A
npm run map:author -- l2 audit-task <concept> --role first-audit --auditor B    # another, for B
```

The orchestrator gives each prompt, unedited, to its own new agent, and nothing else from any other audit. Each
prompt names only that auditor's private findings file
(`.map-authoring/l2/work/<run>/inbox/<subject>/<role>-<auditor>/findings.json`), and `submit-audit` accepts no
other file from that auditor, so two auditors can never write, overwrite or submit each other's findings. Auditor B is
an independent first audit, not a review of A.

No command shows one first auditor's findings before both first audits are in: `l2 findings` withholds a first
audit's findings (and its verdict) until A and B have both submitted, and repair evidence exists only after both
(a concept is reopened only from both first audits). A first auditor's prompt never carries findings.

**Limitation.** Auditors run with shell access in the repository, so nothing technical stops one from listing or
reading files it was told not to (another auditor's inbox, the published artifacts). Independence beyond the normal
workflow rests on the prompt and on the orchestrator never passing one auditor's output to another.

## Submitting findings

An auditor never writes the run state or a group file, and never runs `l2 record`. It writes its findings to the
JSON file its prompt names, and submits that file:

```bash
npm run map:author -- l2 submit-audit <concept> --role first-audit --auditor A --file <json>   # or --auditor B
npm run map:author -- l2 submit-audit <concept> --role re-audit --auditor R --file <json>
npm run map:author -- l2 submit-audit <group> --role group-audit --auditor G --file <json>
```

The file:

```json
{
  "verdict": "pass",
  "note": "What was checked (overlap per placement, territory and splits, representation, accuracy, depth). Advisory: ...",
  "findings": [
    {
      "severity": "blocking",
      "concept": "<id of the record the finding is in>",
      "criterion": "accuracy",
      "evidence": { "quote": "<the exact words from the record>", "location": "paragraph 2" },
      "action": "<what the repair must do, within the accepted territory>"
    }
  ],
  "resolutions": [{ "id": "<signal id exactly as `l2 signals` prints it>", "resolution": "<how it was judged>" }],
  "verifications": [{ "id": "F1", "status": "resolved", "evidence": "<what in the record as it is now shows it>" }]
}
```

- `verdict` is `fail` exactly when at least one finding is `blocking` (severity as in l2-authoring.md, "Finding
  severity").
- Every finding names its concept (a group audit may name any owned member), gives evidence (a quote, which must
  appear verbatim in that record as it is now, a location, or both) and the action it requires.
- A passing first auditor resolves every signal of `l2 signals <concept>`; auditors A and B each resolve what they
  judged, and the recorded audit takes A's resolution where both resolved a signal. A re-auditor and a group
  auditor resolve the signals as in version 1.
- `verifications` only when the task lists the findings a repair answered (F1, F2, ...; "Repair evidence" below):
  exactly one per finding, `resolved` or `unresolved`, with the evidence in the record as it is now. An unresolved
  finding is still blocking, so it is also listed as a blocking finding and the verdict is `fail`. First audits
  carry none.

`submit-audit` validates the file, binds it to the records it judged (the concept's record and every authored
neighbour's, or every member's for a group audit) and publishes it as an immutable artifact under
`.map-authoring/l2/work/<run>/audits/`. A resubmission is a new artifact; nothing is overwritten.

**Freshness.** An artifact counts only for exactly the fingerprints it was bound to. If the concept's record, or any
neighbour's record, changes afterwards (or a neighbour is added or removed), the artifact no longer counts: its
auditor must audit again and resubmit. Auditors A and B are therefore always recorded from the same records and
neighbours. `l2 record audit` says how many earlier artifacts stopped counting.

## Recording (the orchestrator only)

- `l2 findings <concept|group>` shows the artifacts submitted against the current records and what they support
  (first audits only once both are in). It also names, apart and never as current evidence, the concept's
  historical repair findings (`l2 repair-findings`) and how many earlier artifacts judged records that have since
  changed. `--json` prints the current artifacts only.
- `l2 record audit <concept>` records the concept audit from both first audits (or, after a repair, from the
  re-audit). Every artifact is read again and revalidated there (its run, subject, file name, complete binding and
  findings, quotes against the record as it is now), not trusted from submission: a malformed, mismatched or
  invalid artifact refuses the recording. It is refused while an auditor is missing or stale, and on any blocking
  finding. `--audit-file` is refused in a version 2 run.
- Recording is all or nothing: the new group file is built in memory and checked as the `l2-check` gate checks it
  (signals resolved, coverage, fingerprints, repair scope), the run state's step is taken, and only then are the
  group file and the run state written. A refusal at any point leaves both exactly as they were.
- `l2 reopen <id> --from-findings` opens the repair with the blocking findings as its reason (concept, auditor,
  criterion, action and evidence for each), and keeps each concept's own findings as its repair evidence ("Repair
  evidence" below).
- `l2 record group-audit <group>` records the group audit from G's artifact the same way.

## Neighbours

A concept's overlap signals compare its record with its authored neighbours: in version 1, its group's members and
its hazard partners (and, since #243, owned members of other groups that list it). Version 2 adds every concept the
member excludes and the authored concepts its record names (at most 16, in id order, never its own ancestors, whose
texts are judged as parent overlap). Overlaps found there need a resolution like any other.

## Repair evidence

Reopening a concept keeps, on the open repair cycle in the run state, exactly the findings that concept's repair
answers: from `--from-findings`, each of its blocking findings (its own audit's, and a group audit's that name it)
with its provenance, the source artifact's path, binding key and sha256 and the record fingerprint it judged; from
`--reason`, the human's reason. A concept reopened again in the same cycle adds the new findings to its earlier ones.
Artifacts are never copied or rewritten: the evidence points to them.

This evidence is **historical**. It judged the record before the repair, and a sibling's repair can make its
artifacts stale (their neighbour binding no longer matches), but it stays retrievable for the repair workflow:

```bash
npm run map:author -- l2 repair-findings <concept> [--json]   # one concept's findings in the open cycle
```

It prints only that concept's findings, numbered F1, F2, ..., each with its source artifact, and labelled as not
current audit evidence and never an approval. It refuses (non-zero, nothing shown) when the concept is not in an open
repair cycle, when the cycle predates repair evidence, and when any source artifact is missing or no longer the file
it was at the reopening. The same check guards the resolution: `submit-audit` and `l2 record` refuse a re-audit or
group audit whose verified findings have a missing or changed source artifact, and `l2 findings` and `l2 next --json`
report it as inconsistent, for a human to inspect. A stale artifact never counts as a current audit: recording still
takes only artifacts bound to the records as they are now.

Who gets it:
- **The repairer** reads its concept's findings with `l2 repair-findings <concept>` (its task prompt from
  `l2 attempt begin author <concept> --role repair` says so), never `l2 status --verbose` or `l2 findings`, which
  show other concepts' audits.
- **The re-auditor R** is given them in its prompt (`l2 audit-task <concept> --role re-audit --auditor R`), and is
  given no account of the repair. It verifies each in the record as repaired and in `l2 repair-diff`, and submits a
  verification for each (`verifications`, above). `submit-audit` refuses a re-audit that does not account for every
  finding, and `l2 record audit` checks it again on the artifact it records (an inconsistent audit is not recorded).
- **The group auditor G**, when a group audit's findings were repaired in the cycle, is given those findings and
  verifies them the same way. A group audit with no such findings is an ordinary group audit.
- **First auditors** are never given findings.

## Repair diff

When a concept is reopened, its record as the failing audit judged it is kept with the repair cycle.
`l2 repair-diff <concept>` prints, sentence by sentence and entry by entry, what the repair removed, added and kept,
and whether the record's form changed (`--json` for the full diff). The re-auditor reads it to scope the re-audit
([audit.md](audit.md), "Re-audit"): every changed statement, and anything it touches.

## Agent task descriptions

Name each agent task as the cost and budget tooling recognizes it: `Author <id>`, `First audit A <id>`,
`First audit B <id>`, `Repair <id>`, `Re-audit <id>`, `Group audit <group>`.

Every agent's prompt is printed by the tooling: an auditor's by `l2 audit-task`, a draft's or repair's by
`l2 attempt begin author <concept> --role author|repair` (after the line naming its task description). Give it
unedited; add a note only for what the tooling cannot know. Agents report back as their prompt says, in one line
(auditors) or at most three (drafts, repairs); that replaces the step files' "Report back" sections. The outcome of an
audit is read from the tooling (`l2 next --json`, `l2 findings`), not from the auditor's report.

## Orchestrator context

The orchestrator's cost is mostly its own context, read again on every turn (the first v2 pilot: 156 turns at a mean
of about 183k tokens; hand-backs alone added about 77k characters). Keep it small:

- Read [README.md](README.md), this file and [orchestration.md](orchestration.md); [plan.md](plan.md) and the
  l2-authoring.md sections it names when writing a plan. The agents' step files (author, audit, repair,
  group-audit) are for the agents.
- One `l2 next --json` after each action: it carries the step statuses, blockers, operations and the budget, so no
  separate `l2 status` or `l2 budget` is needed between launches.
- Launch prompts as printed; never compose, paraphrase or relay findings (repairers and re-auditors get theirs from
  the tooling).
- Never read an agent's transcript or a whole record to check its work: the audits and gates do that.

## Attempts and recovery

A version 2 run started from now tracks **attempts** ([`attempts.ts`](../../../src/lib/map/authoring/l2/attempts.ts)):
one durable record per launch of a model-driven step (a draft, a repair, each first audit, a re-audit, a group audit),
in `.map-authoring/l2/attempts/<run>.json`. Runs started earlier, and every legacy and simplified version 1 run, do not
track attempts and run exactly as before; `l2 attempts` says so.

**Before launching**, the orchestrator begins the attempt, which persists its input identity (the run, the step, its
role and auditor, the pipeline version, and the fingerprints the step judges: an audit's complete record-and-neighbour
binding; a draft's territory, repair cycle and pre-repair record):

```bash
npm run map:author -- l2 attempt begin author <concept> --role author|repair   # prints the agent's task description
npm run map:author -- l2 audit-task <concept|group> --role .. --auditor ..   # begins the auditor's attempt itself
```

The agent is launched with the printed task description, which carries the attempt's marker (`#att-..`). The budget
hook refuses an Agent launch of a tracked run without a pending attempt's marker, reserves the launch, and marks the
attempt running; a launcher other than the hook launches with `l2 attempt launch <id> --ref <its session reference>`,
which reserves under the same cap (refused, the attempt left pending, when the launch does not fit). An attempt is
launched once: the attempt is marked running inside the reservation's lock, so a second launch of it, even a
concurrent one, is refused and reserves nothing. One attempt publishes one artifact: `submit-audit` checks the
attempt, publishes and completes it under the attempt log's lock, and recording refuses any artifact that is not the
output its attempt captured.

**Its output is bound to its inputs.** `submit-audit --attempt <id>` refuses findings if the evidence changed since the
attempt began; `record author --attempt <id>` refuses a draft whose territory, cycle or pre-repair record changed.
Recording an audit takes only artifacts of completed attempts whose inputs are still the current ones, and records
the step with the attempts it came from. Both first auditors' attempts therefore judged identical, current evidence.

Lifecycle: `pending → running → completed → committed`; `running → interrupted` (no output, outcome unknown);
`interrupted → completed` (its output turns up) or `→ failed` (a decision); any open state `→ failed`. Committed and
failed are final; a duplicate commit is refused.

**Resuming.** `l2 reconcile` compares every attempt with durable evidence (the run state's recorded steps, the
output artifacts, the sessions' own reports and measured cost) and moves it only as that evidence requires:

- an output bound to current inputs completes the attempt, and a recorded step commits it: completed work is reused,
  never launched again (`attempt begin` refuses while a completed output waits to be recorded);
- an output that judged changed inputs, or is malformed or mismatched, fails it;
- a launched attempt with no captured output whose session reports finishing, or that no session has reported within
  15 minutes of its launch (a subagent's transcript can appear after its launch), is **interrupted**: its model call may have completed without its result being captured. Nothing assumes it
  succeeded, and its step cannot be begun again until a human decides
  (`l2 attempt decide <id> --relaunch|--abandon --reason ".."`);
- a session still running is left running (`l2 attempt interrupt <id> --reason ..` once its process is known gone).

Reconciling again changes nothing. `l2 attempts` shows each attempt, what its evidence says and the decision it waits
for, without writing; `l2 attempt show <id>` prints one with its evidence.

**Driving.** `l2 next --json` prints the run's orchestration view, read-only and deterministic: actionable, waiting,
pending, blocked and stale steps, the units and artifacts each expects, the permitted operations, and why each
recorded audit is stale (its own record, or a bound neighbour that changed or disappeared). `l2 batches --slice <id>`
plans a slice as runs of at most 12 concepts. A new version 2 run holds at most 12 concepts, whole groups only: a larger
start is refused, and a slice runs as consecutive batches. Both are specified in [orchestration.md](orchestration.md).

**Budget.** Recovery never frees spending authorization: an attempt keeps the cost measured for its session, which
still counts as spent if the session's transcript is gone; a running or interrupted attempt that no measured session
or budget reservation accounts for holds its role's reserve, and so does a launched attempt resolved without its spend
ever being measured or recorded (failed by a decision, say): deciding what happens to the step says nothing of what
its model call cost. Only an explicit release frees that reserve
(`l2 attempt release <id> --reason ".."`, for a committed or failed attempt), and it is kept on the attempt.
Recorded spend with unpriced or unmeasured calls makes spend unknown, which refuses every launch.

## Crash recovery

Recording a version 2 audit changes the group file and the run state. Both go through a write-ahead journal
([`journal.ts`](../../../src/lib/map/authoring/l2/journal.ts), `.map-authoring/l2/journal/<run>.json`): the journal,
holding each file's new text and current hash, is written first, then each file in order (each replaced atomically),
then the journal is removed. If the process is terminated at any point, the next `l2` command on the run finds the
journal and completes the commit (the files already new are left, the rest written), and says so. If the files are
in any other state (something else changed them), or the journal is malformed, names a file other than the run's
state and the L2 group files, or names one twice, nothing is written and a human decides. A commit is refused while an
earlier one is unrecovered, and when a file is no longer the text it was computed from. A commit, a recovery and
every save of the run state hold the journal's lock, so none acts on another's half-written files.

Completing a commit is not re-validating it. The recovered audit was checked when its recording was decided; if a
record or neighbour it judged has changed since, the recovery says so, and the audit covers nothing it judged
differently: the gates judge it against the records as they are now, like any audit recorded before a change. Attempts are committed right after, and a termination there is completed by
`l2 reconcile` from the step that names them.
